# Study Repository: Master Plan (v2)

## 0. Background and Goals

- **User**: Computer Science student at Monash University Malaysia, on macOS and VS Code, with an existing LaTeX workflow and a mature set of discrete-maths notes, `1058note` (FIT1058, written in LaTeX with theorem environments and `\label`/`\ref`).
- **Goal**: Organise all study material into one large repository arranged by knowledge topic, covering algorithms, programming and mathematics (calculus, linear algebra, analysis, discrete, probability, optimisation). Sources include Monash units, open courses (MIT, UCB, etc.) and reference books (e.g. Rosen, Stewart). **No single source's ordering is authoritative.**
- **Core features**:
  1. Notes are primarily Markdown, one folder per knowledge point.
  2. Selected content can be exported to LaTeX/PDF in the style of 1058note.
  3. Exercises can be filtered to generate practice-paper PDFs.
  4. The repository is also published as a public website (GitHub Pages).
- **First batch scope**: Discrete maths only, FIT1058 scope only. Once the pipeline is proven, extend to Rosen's beyond-syllabus material and other fields.

## 1. Decisions Made

| Item | Decision |
|---|---|
| Organisation | Directories by knowledge topic only; sources (units/books/open courses) are YAML metadata and `sources/` mappings only |
| Note format | Markdown + YAML header; `:::` fenced divs for definitions, theorems, etc. |
| Note language | All English (ids, titles, body, tags) |
| Toolchain | Quarto (website and PDF from one source) + Pandoc Lua filters + Python scripts |
| Outputs | Note PDFs (by manifest), practice-paper PDFs (by filter), public website |
| Visibility | Fully public |
| Exercises | Public repo holds full problem statements (verbatim, not rewritten); the user accepts the copyright risk; solutions go in a separate `solution.md` |
| FIT1058 tutorial/workshop problems and solutions | May be public (unit coordinator CN agreed; user is non-commercial) |
| Assignments, quizzes, exams, original lecture slides, textbook PDFs | **Never enter the repo** |
| Licence | Note content CC BY-NC-SA 4.0; scripts MIT |
| Migrating old notes | Pilot one chapter first, then decide between mechanical conversion and rewriting |
| Time budget | 3–8 hours per week |
| Git | Claude Code never runs commit/add/push; all done manually by the user |

## 5. SPEC Rules

### 5.1 ids and naming

- `id` equals the path without `notes/`, e.g. `math/discrete/logic/propositional/truth-values`; not maintained separately.
- Directory names: lowercase English with hyphens, at most 3–4 levels.
- The top-level taxonomy fixes only the first two levels; leaves are created when needed, no empty directories in advance.
- Provisional discrete-maths branches (the actual 1058note contents win; revised in P1): `logic/propositional`, `logic/predicate`, `proof` (direct, contradiction, induction), `sets-functions`, `relations`, `counting`, `graph`, `number-theory`.

### 5.2 YAML header (`note.md`)

```yaml
---
title: Truth Values
sources: [fit1058-w4, rosen-1.1]
requires: [math/discrete/logic/propositional/statements]
level: core          # core | extra (extra unused in the first batch)
status: draft        # draft | done
---
```

### 5.3 Block types

`definition`, `theorem`, `lemma`, `corollary`, `proof`, `example`, `remark`, `problem`, `solution`, `extra`.

- Blocks that are numbered and referenced use Quarto id prefixes (`def-`, `thm-`, `lem-`, `cor-`, etc.).
- Example:

```markdown
::: {#def-tautology .definition}
A compound proposition is a *tautology* if
$$ p \equiv \mathrm{T} $$
for every assignment of truth values.
:::

::: {.proof}
1. First step.

2. Second step.
:::
```

### 5.4 Exercises and solutions

`exercise.md` (full problem statement verbatim, not rewritten):

```markdown
::: {.problem #prob-induction-03 origin="external" source="fit1058-tut6-q3" difficulty="2" tags="induction,divisibility"}
...full problem statement...
:::
```

`solution.md`, paired with the problem by id:

```markdown
::: {.solution for="prob-induction-03"}
1. ...

2. ...
:::
```

- `origin`: `self` (written by the user) or `external` (textbook, unit, open course).
- If external problems ever need to be taken down, a script replaces every `origin="external"` statement with a citation in bulk.
- `difficulty`: 1–3, filled in by the user; Claude Code does not guess. Leave empty if unknown.

### 5.5 Writing conventions

- Main formulas in definitions and theorems use display maths, not compressed inline.
- Proofs are stepwise (numbered list or separate paragraphs), never one dense block.
- Cross-references use labels only (compiled to `\label`/`\ref`/`\eqref`); never plain text like "§1.6" or "Theorem X".
- Notation follows `meta/notation.md`; notation differences between sources are recorded in the `sources/` mappings.
- Heading levels are not hard-coded; the build script derives `\section`/`\subsection` from directory depth.

### 5.6 Knowledge-point granularity

- One knowledge point ≈ one `\subsection` of 1058note; `note.md` is about 30–150 lines.
- Split only above about 200 lines; isolated definitions under about 10 lines merge into a neighbour.
- Criterion: only the smallest concept cluster that is referenced on its own elsewhere gets its own folder.
- Start coarse: splitting is easier than merging; when splitting, the original id stays as an overview so existing references do not break.
- Examples and exercises are not knowledge points; they go in that point's `example.md` / `exercise.md`.

### 5.7 SPEC freeze

Revise once after the P3 pilot and freeze as v0.2. Do not change structure while migrating the first 20 knowledge points; record wanted changes in `meta/ideas.md` and apply them in one batch afterwards.

## 6. Build and Outputs

All three outputs share the same Markdown and the same Lua filters:

| Output | Entry point | Process |
|---|---|---|
| Note PDF | `views/xxx.yml` (hand-written manifest) | `make_note.py` reads the manifest, derives heading levels from directory depth, assembles a temporary `.qmd`, runs `quarto render` to PDF using `meta/preamble.tex` |
| Practice-paper PDF | `papers/xxx.yml` | `make_paper.py` scans `problem` blocks in `exercise.md`, filters by path/difficulty/tags/origin, optionally appends `solution.md` |
| Website | `quarto render` | Sidebar from Quarto's directory auto-listing or a script; GitHub Actions builds and publishes to Pages |

Manifest example (`views/fit1058-review.yml`):

```yaml
title: FIT1058 Review
include:
  - path: math/discrete/logic/propositional
    files: [note, example]
  - path: math/discrete/proof/induction
    files: [note, example, exercise]
options:
  include_extra: true
  order: manifest      # manifest | tree | requires
```

Practice-paper spec example (`papers/induction-practice.yml`):

```yaml
title: Induction Practice
select:
  path: math/discrete/proof/induction
  difficulty: [1, 2]
  tags: [divisibility]
options:
  count: 10
  solutions: false
```

`make` targets: `make check`, `make note VIEW=views/x.yml`, `make paper SPEC=papers/x.yml`, `make site`.

`check.py` checks:

- Duplicate ids, broken references
- Missing YAML fields
- `problem` missing `origin` or `source`
- Missing problem–solution pairs
- `requires` pointing to non-existent nodes
- Accidental inclusion of `raw/`, PDFs, `.aux` or other files that must not be committed

## 7. Copyright, Compliance and Licensing

- **CN's consent**: Keep the original record (email or message screenshot, stored privately, not in the repo). Two points to confirm: whether it covers a public website, and whether it covers both statements and solutions. `PROVENANCE.md` contains only a one-sentence summary.
- **README notice**: Third-party problems remain the copyright of their original authors and are quoted for study only; CC BY-NC-SA covers only the author's own content.
- **Textbook problems (Rosen, Stewart, etc.)**: The user accepts the risk; `origin="external"` guarantees bulk takedown is possible.
- **Never in the repo**: Assignments, quizzes, exams, original lecture slides, textbook PDFs. These also involve academic-integrity policy, not just copyright.
- **`out/` is not committed**: avoids publishing practice papers that compile external problem statements.

## 8. Working with Claude Code

### 8.1 Division of labour

| User | Claude Code |
|---|---|
| Reviews SPEC, decides taxonomy and granularity | Drafts SPEC/taxonomy, builds the skeleton |
| Reviews every converted note against the original PDF | Pandoc conversion, splitting, adding YAML and block markup |
| All `git add` / `commit` / `push` | Writes Lua filters, build scripts, `check.py`, CI config |
| GitHub web settings (Pages, visibility) | Read-only checks (`git status`, `git diff`, `find`) |
| Fills in `difficulty`, verifies `source` | Never guesses, never fabricates |

### 8.2 Guardrails first, then start Claude Code

The user hand-writes `.claude/settings.json`:

```json
{
  "permissions": {
    "allow": [
      "Bash(git status *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "deny": [
      "Bash(git add *)",
      "Bash(git commit *)",
      "Bash(git push *)",
      "Bash(git * commit *)",
      "Bash(git * push *)",
      "Bash(git reset *)",
      "Bash(git rebase *)",
      "Bash(git merge *)",
      "Bash(git checkout *)",
      "Bash(git restore *)",
      "Bash(git clean *)",
      "Bash(git stash *)",
      "Bash(git config *)",
      "Read(./raw/**)"
    ]
  }
}
```

- Permission rules are enforced by Claude Code, evaluated in the order deny, ask, allow. Instructions in CLAUDE.md only shape what Claude tends to do; they cannot change what it is allowed to do. So "no commits" is hard-blocked by deny rules, and CLAUDE.md is only a supplement.
- After starting, confirm the rules are active with `/permissions`.
- No git write commands in the Makefile or scripts, because calls inside scripts bypass the Bash rules.
- Optionally put the same deny rules in the user-level `~/.claude/settings.json` so other projects are covered too.

### 8.3 CLAUDE.md (English, hand-written by the user at the repo root)

```markdown
# Study repo: rules for Claude Code

Public study-notes repo. Notes are Markdown + YAML, built with Quarto and Pandoc Lua filters.
Read meta/PLAN.md and meta/SPEC.md before any task.

## Hard rules
- NEVER run git add, commit, push, reset, checkout, restore, stash, or config. The owner does all git operations.
- At the end of every task, list the changed files and propose ONE commit message (prefix: feat, migrate, fix, build, docs, chore). Do not commit.
- NEVER read, write, or reference raw/. Never add assignments, quizzes, exams, lecture slides, or textbook text.
- Do not invent taxonomy nodes, rename ids, or change YAML fields without asking.
- Never put git write commands in scripts or the Makefile.

## Content rules
- Notes are in English.
- Copy problem statements verbatim. Never paraphrase or shorten them.
- Never fabricate sources. If a source is unknown, leave `source` empty and add a TODO comment.
- Mechanical migration means convert and tag only. Do not rewrite or improve the author's wording. Set `status: draft`.
- Every `problem` block needs `origin` and `source`. Each solution is paired by id in solution.md.
- Proofs: numbered steps, separate paragraphs, no dense blocks.
- Display math for definitions and theorems. Cross-references use labels, never plain text like "Section 1.6".
- Follow meta/notation.md for symbols.

## Structure
- One knowledge point per folder under notes/: note.md, example.md, exercise.md, solution.md (only note.md is required).
- id equals the path without the notes/ prefix. Folder names are lowercase English with hyphens.
- Granularity: about one subsection, 30-150 lines. Split above 200 lines, merge below 10.

## Workflow
- One task per session. Keep changes small and reviewable.
- Run `make check` before reporting a task done.
- If a request conflicts with these rules or SPEC, stop and ask.
```

### 8.4 The user's commit flow (once per task)

```bash
git status
git diff --stat
git diff                       # review every hunk; check notes against the original PDF
make check
git add <specific paths>       # never git add -A, to avoid pulling in raw/ or PDFs
git commit -m "migrate(discrete): logic/propositional truth-values"
git push                       # after a batch of tasks
```

Commit prefixes: `migrate` (old notes brought in), `feat` (new notes/features), `build` (filters/scripts/CI), `docs` (SPEC/README/taxonomy), `fix`, `chore` (skeleton/ignore/config). Granularity: one knowledge point or one chapter per commit, one kind of change at a time. Optional: a self-configured `.git/hooks/pre-commit` that refuses to stage `raw/`, `*.pdf`, `.env`.

### 8.5 Session prompt template

```
Task: <one sentence>
Context: read CLAUDE.md and meta/PLAN.md first.
Input: <file or directory>
Output: <files to produce>
Constraints: no rewriting of wording; verbatim problem statements; do not touch git.
Done when: make check passes; list changed files and propose a commit message.
```

## 10. Per-Chapter Migration Loop

1. Claude Code: Pandoc-convert the chapter's `.tex` to md, split into knowledge-point folders per SPEC, add YAML, convert environments to `:::` blocks, add problem attributes.
2. User: review item by item against the original PDF, fix; fill in `difficulty`.
3. `make check` passes.
4. User manually `git add`s specific paths and commits.
5. Delete the corresponding part of `legacy/` in a separate commit (`chore`).

## 11. Daily Workflow

1. Learning or revising a topic: find its place in `taxonomy.md`; add it first if missing.
2. Create the knowledge-point folder and write `note.md` (Claude Code may draft; the user rewrites in their own words).
3. Put examples, exercises and solutions in their files.
4. `make check`, then commit yourself per §8.4.
5. For revision material: write a manifest for a note PDF, or a papers spec for a practice paper.
6. `git push` after each batch of commits; the website updates automatically.

## 12. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Assignments, exam questions or slides leak into the public repo | `raw/` is in `.gitignore` and under a `Read` deny; only `git add <specific paths>`; optional pre-commit hook; `check.py` check |
| Claude Code commits on its own | Deny rules hard-block it; verify with `/permissions` after start; scripts contain no git write operations |
| Claude Code rewrites problem statements or fabricates sources | Explicitly forbidden in CLAUDE.md; user checks `source` and statements against originals |
| External problems must be taken down | `origin="external"` + bulk replacement script; `out/` not committed |
| Perfectionism causes delay | Time boxes; P4 only requires "close"; SPEC freeze; migrate mechanically first, polish later; tooling ranks below content |
| Quarto's custom-block support is insufficient | Verify in P3; fall back to Lua filters if needed; the md itself is unaffected and portable to other tools |
| Repeated taxonomy changes | At most 3–4 directory levels; record wanted changes in `ideas.md` and adjust once in a batch |
| Referenced nodes not exported | Script warns or pulls them in based on `requires` |
